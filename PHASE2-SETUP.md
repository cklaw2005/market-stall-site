# Phase 2 setup

Phase 1 remains the public menu and WhatsApp order flow. Phase 2 adds website accounts, saved customer preferences, online orders, seller weighing/pricing, and customer confirmation.

## Login model

- The stall owner can create as many customer accounts as needed in the seller dashboard; there is no fixed account cap.
- Each account has a customer name, phone number, and selected favorite products.
- The site generates a strong temporary password and shows it to the owner once. Give it to that customer privately.
- The customer signs in with the phone number and temporary password. The first screen requires a new password before any order data is shown.
- If a customer forgets their password, the owner resets it and gives them a new temporary password. There is no SMS gateway, OTP, Google OAuth, or public self-registration.
- The owner account is created once by the project administrator in Supabase Auth and authorized for the stall. It can then create, reset, and deactivate customer accounts.

## Remaining owner account setup

1. Choose the stall owner's phone number and initial password. In **Authentication → Users**, create the owner user with internal email identifier `60` plus the phone digits followed by `@login.market-stall.invalid`, mark the email as confirmed, and copy the resulting user UUID. The owner still enters the phone number on the website login screen.
2. Add the owner profile and restaurant membership in SQL Editor, replacing `OWNER-USER-UUID` and `+60XXXXXXXXX` with the selected owner UUID and phone:

   ```sql
   insert into public.profiles(user_id,display_name,phone,restaurant_id,role,active,must_change_password)
   select 'OWNER-USER-UUID'::uuid,'摊主','+60XXXXXXXXX',id,'owner',true,false
   from public.restaurants where slug='dad-vegetable-stall'
   on conflict(user_id) do update set display_name=excluded.display_name,phone=excluded.phone,
     restaurant_id=excluded.restaurant_id,role='owner',active=true,must_change_password=false;

   insert into public.restaurant_memberships(restaurant_id,user_id,role)
   select id,'OWNER-USER-UUID'::uuid,'owner' from public.restaurants where slug='dad-vegetable-stall'
   on conflict(restaurant_id,user_id) do update set role='owner';
   ```

3. Sign in as the owner at `https://cklaw2005.github.io/market-stall-site/phase2.html`, create a test customer, and verify first-login password change and the order → final weight/price → customer confirmation flow before inviting real customers.

## Account and data safeguards

- Customer account count is not capped. Each new account receives a permanent increasing customer number. Deactivated customers keep their old orders for history but cannot sign in; reactivation assigns the next number and issues a fresh temporary password.
- Customer profiles are provisioned/changed only by the trusted Edge Function or the administrator. The browser cannot change its own role, active status, restaurant assignment, or first-login password flag.
- Owners can manage only customers assigned to a restaurant where they have an owner/manager membership.
- Temporary passwords are generated by the server and are not saved as plaintext. The owner must copy or record each one when it is shown; it will not be displayed again.
- Customer phone numbers identify the internal login account but are not verified by SMS. If the customer loses access, the stall owner resets the password.
- The service-role key is a secret. Never commit it, put it in `supabase-config.js`, or send it to customers.

## Existing order behavior

- The first owner login seeds the existing catalog into that restaurant's menu table. Owners can reorder items; the public menu reflects the saved order.
- The Phase 2 customer page reads the published Google Sheet price feed and stores the requested values on each order. The owner enters final quantity/weight and final price; database functions calculate the total.
- Customers may optionally request equal portions for kilogram-based items. The split count is stored as a packing instruction and shown to the owner and customer. It does not enter the amount formula: the total remains based on seller-confirmed final weight and unit price.
- The owner publishes a final order revision. The customer signs in to review and confirm it. WhatsApp is not the order database or calculator.
- Keep the current public menu/Phase 1 flow available. Do not describe Phase 2 as live until the Supabase project, Edge Function, customer onboarding, and complete order path work on the published site.
